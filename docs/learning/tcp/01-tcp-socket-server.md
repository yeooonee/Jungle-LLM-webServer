# TCP 소켓 서버: 연결과 바이트 스트림

## 목표와 선수지식

C의 배열, 포인터, 반복문, 함수 반환값을 바탕으로 TCP 연결 수락과 송수신 흐름을 설명한다.
이번 구현은 IPv4 TCP 에코 서버다. 받은 바이트를 그대로 돌려주며 HTTP 해석은 하지 않는다.
동시성 모델과 프록시 방식은 아직 결정하지 않았다.

## 1. 소켓과 실행 흐름

소켓은 운영체제가 관리하는 통신 자원이다. 프로그램은 정수 파일 디스크립터(fd)로 다룬다.

```text
서버                               클라이언트
socket()                           socket()
  ↓
bind()       로컬 IP·포트 지정
  ↓
listen()     연결을 받는 상태
  ↓
accept() ←──── TCP 연결 ────────── connect()
  ↓
recv()   ←──── 바이트 ──────────── send()
send()   ───── 바이트 ──────────→ recv()
  ↓
close()                            close()
```

- `socket(AF_INET, SOCK_STREAM, 0)`: IPv4 TCP 소켓 생성.
- `bind()`: 소켓에 로컬 주소를 지정.
- `listen()`: 연결을 수락할 리스닝 소켓으로 전환.
- `accept()`: 연결 하나의 **새 fd** 반환. 리스닝 fd는 계속 유지.
- `recv()` / `send()`: 연결 fd로 데이터 수신 / 송신.
- `close()`: fd 해제. 리스닝 fd와 각 연결 fd를 각각 정리한다.

리스닝 소켓을 닫아도 이미 수락한 연결 소켓은 독립적으로 남는다.
새 연결을 다시 받으려면 리스닝 소켓을 준비해야 한다.

## 2. IP·포트와 연결 성립

- `127.0.0.1:8080`: 같은 컴퓨터에서만 접속.
- `0.0.0.0:8080`: 모든 로컬 IPv4 인터페이스에서 연결 수신.
- 다른 컴퓨터에서는 서버의 실제 IP(예: `192.168.0.10:8080`)로 접속.
- 외부 접속 가능 여부는 방화벽과 네트워크 환경에도 달려 있다.
- `htons()` / `htonl()`: 포트 / 주소를 네트워크 바이트 순서로 변환.

운영체제의 TCP 구현이 SYN → SYN+ACK → ACK의 3-way handshake를 처리한다.
`connect()` 성공은 TCP 연결 성립을 뜻한다. 서버 프로그램의 `accept()`나 요청 처리가 끝났다는 뜻은 아니다.
연결은 서버 쪽 대기열에서 수락을 기다릴 수 있다. `listen()`의 backlog는 동시 처리 스레드 수가 아니다.

## 3. TCP는 메시지 경계를 보존하지 않는다

```text
송신: send("hello") + send("world")
수신 가능 예: "hello" + "world"
              "helloworld"
              "hel" + "lowor" + "ld"
```

`send()` 호출 횟수, TCP 패킷 개수, `recv()` 호출 횟수는 메시지 개수와 같지 않다.
메시지 경계는 애플리케이션 규칙으로 정한다.

- 고정 길이: 항상 100바이트.
- 구분자: `\n`까지 한 메시지.
- 길이 표시: 길이를 먼저 전달하고 그만큼 본문 수신.

줄바꿈 규칙에서 `hello\nwor`를 받으면 `hello` 하나가 완성됐고 `wor`는 보관한다.
`hello\nworld\n`는 한 번에 받았어도 두 메시지다.
HTTP는 헤더 끝을 `\r\n\r\n`으로 구분한다. `Content-Length`가 본문 길이를 정하는 경우에는 그 길이만큼 읽는다.
HTTP의 다른 길이 결정 규칙은 이후 학습 범위다.

## 4. 부분 수신과 종료

| `recv()` 반환값 | 의미 |
|---|---|
| 양수 | 이번에 실제로 읽은 바이트 수 |
| `0` | 상대의 정상 송신 종료를 확인했고 남은 수신 데이터도 없음 |
| `-1` | `errno`로 원인을 구분해야 하는 오류 |

100바이트를 받기로 했다면 40 → 25 → 35바이트로 나누어 받을 수 있다.
누적 길이를 추적하고 기존 데이터 뒤에 이어서 저장한다.
40바이트 뒤 `0`을 받으면 약속한 메시지가 불완전하게 끝난 것이다. 나머지를 기다리지 않는다.

블로킹 소켓에서 데이터가 아직 오지 않았다는 이유로 `0`을 반환하지 않는다.
상대가 송신을 종료해도 버퍼의 데이터를 먼저 읽고, 이후에 `0`을 받는다.
TCP는 양방향이므로 상대의 송신 종료가 서버의 송신 방향 종료까지 뜻하지는 않는다(half-close).

## 5. 부분 송신과 재전송의 차이

`send()`의 양수 반환값은 로컬 운영체제가 받아들인 바이트 수다.
상대 프로그램이 읽거나 요청 처리를 끝냈다는 뜻이 아니다.

```text
100바이트 전송 시도
send() → 40
send() → 25
남은 위치: buffer + 65  (사람 기준 66번째 바이트)
남은 길이: 35
```

부분 송신 이후에는 프로그램이 아직 받아들여지지 않은 나머지를 보낸다.
이미 받아들인 데이터를 처음부터 다시 보내면 중복 데이터가 된다.
반면 네트워크 손실에 대한 TCP 재전송은 운영체제가 처리한다.

## 6. 버퍼·ACK·흐름 제어

`accept()` 전에도 연결의 데이터가 운영체제 수신 버퍼에 보관될 수 있다. 버퍼 크기는 유한하다.
TCP는 다음 정보를 상대 TCP에 전달한다.

- ACK 번호: 연속으로 수신한 바이트 다음에 필요한 바이트 번호.
- 수신 윈도우(rwnd): 수신 측이 받아들일 수 있다고 알리는 데이터 범위.

송신 측은 이미 전송했지만 확인받지 못한 데이터까지 계산해 전송량을 제한한다.
실제 전송량은 네트워크 혼잡 제어의 제한도 받는다.

```text
서버가 recv()하지 않음 → 수신 버퍼가 참 → 수신 윈도우 축소
→ 클라이언트 전송 제한 → 송신 버퍼도 참 → 블로킹 send() 대기 가능
```

공간 부족 등으로 패킷이 버려질 수는 있다. TCP가 손실을 감지해 재전송하므로,
정상 연결에서 애플리케이션이 중간 바이트를 조용히 건너뛰어 받는 방식은 아니다.
복구할 수 없는 연결 실패는 오류로 처리해야 한다.
ACK는 운영체제의 수신 확인이며 애플리케이션 처리 완료 확인이 아니다.
TCP 원리는 [RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)을 참고한다.

## 7. 오류는 각자의 운영체제가 알려준다

클라이언트와 서버 모두 같은 소켓 API를 사용하고 오류를 처리한다.
`errno` 자체를 상대에게 보내는 것은 아니다. 실패한 호출 직후 자기 프로세스에서 확인한다.

| 상황 | 처리 |
|---|---|
| `EINTR` | 시그널로 호출 중단. 종료 요청이면 종료, 그 외에는 재시도 |
| `ECONNRESET` | 연결 강제 초기화. 해당 연결 정리 |
| `EAGAIN` / `EWOULDBLOCK` | 논블로킹에서 지금 진행 불가, 또는 설정한 소켓 대기 시간 만료 |
| `EPIPE` | 송신 불가능한 연결에 쓰기. 해당 연결 정리 |

`EPIPE` 상황에서 `SIGPIPE`도 발생할 수 있다. 기본 동작은 프로세스 종료이므로 서버는 이를 무시하도록 설정하고 반환값으로 오류를 처리한다.
같은 순간에 양쪽에서 같은 오류를 관찰한다는 보장은 없다.

## 8. 블로킹과 이번 코드의 범위

한 스레드가 A의 `recv()`에서 기다리면 그동안 B를 직접 처리하지 못한다.
운영체제가 B의 연결을 대기열에서 관리하는 것과 프로그램이 B를 처리하는 것은 다르다.
이번 서버는 한 연결이 끝난 뒤 다음 연결을 처리하는 순차 모델이다.
동시 처리 방식은 이후 사용자가 선택한다.

- `main.c`: 포트 검증, `sigaction()`, 종료 플래그, `SIGPIPE` 무시.
- `net/tcp.c`: 리스닝 소켓 준비, 연결 수락, 바이트 에코, fd 정리.
- 리스닝 소켓은 `poll()`로 대기한다. 준비 상태가 사라져도 `accept()`가 멈추지 않도록 리스닝 fd만 논블로킹으로 둔다.
- 연결 소켓은 명시적으로 블로킹으로 설정한다.
- 송수신 대기는 250ms로 제한한다. 만료 시 연결을 끊지 않고 종료 플래그를 확인한 후 재시도한다.
- 이는 유휴 연결 제한 시간이 아니다. 종료 요청이 없으면 유휴 클라이언트가 다음 연결 처리를 계속 막을 수 있다.
- `poll()`은 여기서 리스닝 fd 하나를 기다리는 용도다. 여러 클라이언트를 관리하는 이벤트 루프는 아직 없다.
- `SO_REUSEADDR`는 `bind()` 전에 설정한다. 사용 중인 리스닝 포트를 빼앗는 옵션은 아니다.
- 시그널 핸들러는 `volatile sig_atomic_t` 플래그만 설정한다. 정리는 일반 실행 흐름에서 수행한다.
- 종료 요청 시 현재 연결도 닫는다. 응답을 모두 배출하는 graceful shutdown은 아직 구현하지 않았다.

## 9. 실행과 관찰

```sh
make
./build/webserver 8080
```

다른 터미널에서:

```sh
nc 127.0.0.1 8080
```

문자를 입력하고 Enter를 누르면 입력한 줄이 에코로 다시 출력된다.
`nc`의 로컬 입력 표시까지 있으면 같은 줄이 두 번 보일 수 있다.
서버 터미널에서 Ctrl+C를 누르면 종료한다.

```sh
make test-integration
make asan
python3 tests/integration/test_tcp.py build/webserver-asan
```

자동 테스트는 잘못된 포트, 포트 충돌, 나누어 보낸 데이터, 빈 송신 종료,
2 MiB 바이너리 에코, half-close, 강제 연결 종료 후 재접속, 재시작,
유휴/송신 정체/연결 대기 상태에서의 종료를 확인한다.
분할 송신 테스트가 특정 `recv()` 분할이나 `send()` 부분 반환을 강제로 보장하는 것은 아니다.
